# 振り返りフェーズの設計メモ

> 学習が終わったら、**結果が出る前に**これをやる。
> E資格（100問）と統計検定2級（41問）の2回で、実際に機能した手順を型にしてある。

---

## ★ 鉄則: 合否・結果が出る前にやる

**結果を知った後の記憶は、結果に引っ張られる。**
合格すれば全部正しかったことになり、不合格なら全部間違っていたことになる。
だから**結果が入る前に証言を凍結する。**

結果が出たら、書き換えずに**追記**する。追記の観点は3つだけ:

1. 本人の手応え（自己評価）は当たっていたか ← 較正精度。次回の判断材料になる
2. 最大の反省として挙げた項目は、実際に何点分だったか
3. **結果によって変わる結論はあるか** — 原則ない。
   もし変わるものがあったなら、それは**結果に引っ張られているサイン**として疑う

### その場で結果が出る試験（CBT など）のとき

結果の前に凍結することは、もともとできない。代わりに次の2つをやる。

- **本番の報告を受けた同じ返事で、3つ聞く**（`CLAUDE.md`「Claude が守ること」17）: 分からなかった問題の分野と中身・時間配分・手応え。
  統計検定2級では聞かず、5日後の回答は「全くわからなかったのが6問くらいありました。どの単元かは忘れた」だった。本番の分野別の偏りを説明できる記録が残らなかった
- **効いたかどうかを、合否ではなく摩擦で判定する**（読んだか・時間・迷い）。反省まとめの最後に「結果との関係」の節を置き、条件が恵まれていた点も書く

---

## 手順

### 1. 事実台帳を作る（Claude / 半日）

振り返りの前に、**数字と出来事を時系列で並べる**。記憶ではなく記録から。

> ★ **`project-plan.md` §6 を軸にする。** §6 には、学習中の指摘・要望・決定が**その場で**1行ずつ足してある（`CLAUDE.md` 守ること 13）。
> 事実台帳は §6 の時系列から始め、設問は「§6 に記録の無い期間・領域」と「§6 で決めたことが、その後どうなったか」に絞る。

- 週次の進捗（計画 vs 実績）
- 台帳の全指標（周回ごとの正答率・確信ある正解・逆行率・転換率・分野別）
- 計画変更の日付と、そのとき提示した数字。**誰が言い出したか**（Claude の発火条件か、User か）
- 「決めたのに実行されなかった」事象の一覧。**器はあったのに使われなかった欄**も数える（書かれた回数）
- git の記録から数えられるもの（一問一答を解いた時刻 = `python ledger/daily.py pace`、手書きページに書き込みのあった枚数）
- 本人の証言（`project-plan.md` §6）

出力: `retrospective/00_事実台帳.md`

### 2. 設問を作る（Claude / 40問前後・★必須はその半分）

**数の決め方**: §6 が厚ければ40問前後で足りる（統計検定2級は §6 が77行あり、41問・★19問。学習者「設問少ないからそんな苦労しなかった」）。
§6 が薄い・期間が長いときは増やす（E資格は §6 の運用が無く、100問だった）。**★（必須）と任意に分け、必須は半分まで。**

**構成**（統計検定2級の41問の実績）:

| 部 | 割合 | 内容 |
|---|---|---|
| 1. 運用を固める | 約45% | 最初の1問で、§6 で決めた運用を並べ、それぞれ「続ける／直して続ける／やめる／分からない」で仕分けてもらう。続けて、計画とガント・解説と図・一問一答・手書きページ・Claude の報告と提案 |
| 2. 新しい発見 | 約40% | 記録に残っていないこと: 本番・時間と生活・何が効いたか（効いた順）・使わなかったもの・道具と環境 |
| 3. 次へ持ち出す | 約15% | 持ち出すもの・二度とやらないもの・次の学習・**この振り返り自体の形**（最後に答えてもらう） |

**必ず入れる設問**:

- **「`THIS-WEEK.md`・`STATUS.md`・`project-plan.md` のうち、自分で開いたものはどれか。開いたなら何のために」** —
  人が見る画面を3つ（ガント・学習ページ・`THIS-WEEK.md`）に絞った設計が合っているかを、毎回確かめる。
  特に `THIS-WEEK.md` は、E資格（`TODAY.md`）・統計検定2級と2回続けて開かれず、「まだやっていない行を先頭に置く形」に直したところ。直した形で開かれたかを聞く
- `project-plan.md` §7「テンプレートの検証項目」の各行を確かめる設問

**設問の書き方（ここが一番大事）**:

- **すべて記述式。** 選択式にすると、用意した選択肢の中でしか答えが返らない
- **Claude の仮説を書かない。** 「事実: ◯◯」だけを記憶の呼び水として添える。
  仮説を書くと回答がそれに引っ張られる（アンカリング）
- **「わからない・覚えていない」も有効な回答**だと明記する。
  それ自体が「記録が足りなかった」という発見になる
- **数字を添える。** 「ある分野が 28% → 69%」のような具体値があると記憶が戻る
- ★ **Claude 側の仕組みや過去のやり取りを聞くときは、User から見えていた形で書く。**
  仕組みの名前（「§6」「タスクの番号」）や、やり取りの細かい段階で聞くと止まる。
  統計検定2級で止まった4問は全部これだった（「§6 の記録を意識していたか」→「どゆこと？」）。
  ✗「§6 の運用を続けるか」 → ✓「計画書の末尾に、あなたの言葉をそのまま書き写していた。これを続けるか」
- **「事実と違うと感じたら、そこを指摘してほしい」**と書く（台帳の誤りが見つかる）

出力: `retrospective/01_振り返り_設問.md`

### 3. 回答してもらう（既定は、チャットで1問ずつ）

**チャットで1問ずつ出し、答えを Claude が原文のまま書き写す**のを既定にする
（学習者「1問ずつデフォルトはこのチャット上でできるとよい」）。ページに書き込んで push する形も選べるようにしておく。
「順不同でよい」「何回に分けてもよい」「番号さえあれば拾う」と伝え、**回答の期日を User に決めてもらう**。

出力: `retrospective/01_振り返り_回答.md` — **原文ママで保存する**（誤変換も直さない）。
解釈は次のステップでやる。一次資料に手を入れない。

### 4. 分析する（Claude）

出力: `retrospective/02_反省まとめ.md`。構成は次の6つ。

1. **結論を先に3つ**
2. **発見** — 各項目に「根拠となる回答 / 何が起きていたか / 次にどうするか」
   - 回答をまたいで**同じ型の失敗**を探す（3件揃えば構造的な問題）
   - 本人が別々のこととして答えているものを**束ねる**のが Claude の仕事
   - 「今回は期間が短かったから」と断られた運用を分ける（そのまま次の既定にしない）
3. ★**答え合わせ** — Claude が前提にしていたことが、どこで外れたか
   - 設問に仮説を書かなかったからこそ、これができる
   - 仮説を前もって書いた記録が無ければ、**学習中に計画や教材の作り方で前提にしていたこと**を回答と照らす
   - 前回の振り返りからテンプレートに入れた仕組みが、今回どうだったかの表も置く
   - **外れた前提は処方が変わる**ので、ここが一番価値がある
4. **設計要求**（P0 / P1 / P2 に分け、出典の設問番号を必ず付ける。本人が明示したものと、Claude がまとめて導いたものを分ける。「いまのテンプレートに入っているか」の列を置く）
5. **未解決の論点** — 回答どうしや、既存の決まりと食い違っている箇所を、案を添えて本人に確かめる
6. **結果との関係** — 手応えは当たっていたか・条件は恵まれていたか・最大の反省は何点分だったか

**反省まとめと設問への回答は別の作業**。User に状態を伝えるときは、各行の頭に誰の作業かを書く
（「論点に答えてもらう」とだけ書いて、41問にもう一度答えるのかと受け取られた）。

### 5. 汎用資産を抜き出す

設計要求のうち再利用できるものを、テンプレートとスキルへ落とす。

- **テンプレートに入れて push したところで閉じる。** 次の学習が決まっていなくても待たない
- **効いたかは、次の学習で確かめる。** 直した形を `study-init` スキルの「前の振り返りで直した形を確かめる」の表に足す。
  次の立ち上げでその表が `project-plan.md` §7 に写され、次の振り返りで結果が書かれる（作って終わりにしない）
- 反省まとめの末尾に「反映した要求／見送った要求と理由」の表を足す

## 分析のコツ

### 矛盾を潰さない、論点として出す

E資格では「効いたのは NotebookLM」と「NotebookLM 依存を外して」が同居していた。
これは**矛盾ではなく要求**だった（＝「同等以上のものを自作しろ」）。
統計検定2級では「見なくて良かった」と「二度とやらないものは特にない」が同居し、確かめると「形を直して使う」だった。
無理に整合させず、本人に確かめる。

### 「本人が気づいていない束ね方」を探す

- 4件の別々の遅れ → 全部「実力や範囲を測る行為を後ろに置いた」の同じ型
- 3件の別々の「わからない」 → 全部「Claude の内部語彙が届いていない」
- 7件の別々の「聞いてほしい」 → 全部「計画に属するもの」（中身は聞かずに進めてよい）

**本人はバラバラに答える。束ねるのが分析。**

### 効いた/効かなかったを、効果ではなく摩擦で見る

「効果が実証されているのに実行されなかった」ものは、
説得の失敗ではなく**環境の未整備**であることが多い。
「どこに書くか」が決まっていなかっただけ、というケースが実際にあった。
**器があっても、それを見て動く決まりが無ければ同じ**（量を調整するための欄は、書かれるのを待つだけで、誰も見ていなかった）。

### 読まれたかどうかは、中身ではなく置き場所で決まる

同じ分析でも、解説の中に書いたものは「助かりました」と言われ、ページ冒頭の所見に書いたものは読まれなかった。
「読まれなかった文章」を見つけたら、中身を直す前に、置き場所を疑う。
