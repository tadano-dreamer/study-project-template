# study-review — 進捗レビュー

## やること / やらないこと

| やる | やらない（別セッションへ） |
|---|---|
| 状態復元・信号判定 | 演習の**採点**（→ drill-ledger） |
| 数字で詰める・リプラン提案 | 教材の**生成・配信** |
| STATUS / ガント / 進捗ログの更新 | 想起テストの**出題**（→ recall-drill） |

理由: レビューと生成を同じセッションでやるとコンテキストが膨らみ、
次のレビューが重くなる。**レビューは軽いままにしておく。**

## 起動手順（最小コンテキスト）

1. `STATUS.md` を読む ← 起点
2. `THIS-WEEK.md` を読む
3. 台帳があれば `python ledger/tally.py` を1回
4. ここまでで足りなければ、`project-plan.md` の**進捗ログの末尾だけ**部分読み。全読みしない

## 信号の判定

| 信号 | 条件 | 対応 |
|---|---|---|
| 🟢 | ベースライン比の遅れ 7日未満 | そのまま。次のゲートまでの必要ペースを1行で示す |
| 🟡 | 遅れ 7〜20日 / 1週間 進捗報告なし | 原因を3択以内で聞く（時間不足 / 本業 / モチベ）＋必要ペースを数字で |
| 🔴 | 遅れ 21日以上 / 2週連続で動きなし / 通し演習が合格ラインの -15pt | **数字で詰める。かつ必ず `study-replan` を起動する** |

遅れはガントが自動算出する（棒の後端 − 今日）。**自分で数えない。**

## 「数字で詰める」の作法（User 指定 / これ以上はやらない）

E資格で実際に効いた形は、次の2つまで。

1. **数字で突きつける** — 残日数・必要ペース・現在ペース・その差。感情を混ぜない
2. **実行の宣言を求める** — 「いつ何をやるか」をその場で言ってもらい、
   **次のセッションの冒頭で必ず答え合わせをする**

罰や機能停止のような演出はしない。逃げ道は塞ぐが、学習そのものは止めない。

> 効いた実例（User 談）: 「数字で詰めますって言われたのはかなりやらなきゃなと思えました」
> 効かない実例（User 談）: 「声に出すとかそういうのは効果ない」

## ★ 開始時にガントへ即反映する

User が進捗を報告したら、**その場で** `wbs-gantt/wbs-gantt_v<N>.html` を更新する。
終了時にまとめようとしない。セッションが正式に閉じない日があり、
ためるとガントが古いまま残る（E資格で指摘を受けて恒常化したルール）。

更新するのは `TODAY` / 各タスクの `st`・`pct` / `COMMENTS` **だけ**。
ベースライン `s`・`d` は**絶対に触らない**（伸ばすと遅れが消える）。
編集後は PNG の更新時刻を確認し、古ければ手で再生成する。

## 🟢 を出すときの必須処理

**🟢は「今は触らない」であって「もう安全」ではない。**

🟢を出した分野は、`STATUS.md` に**再測定の期限**を書く。期限が来たら小テストで測り直す。

E資格では、2周目で🟢判定を出して触らなかった3分野が、初見の通し演習で
-18pt / -14pt / -9pt と崩れた。User は苦手意識を持っていなかったので
（判断を全面的に Claude へ委ねていたので）、**誰も止められなかった。**
全委任を続けるなら、この再測定が唯一の安全弁になる。

## セッション終了時（User が終了を明示したときだけ）

1. `STATUS.md` を最新化 ← 次のレビューを軽く保つ生命線
2. `project-plan.md` の進捗ログへ1エントリ（日付 / 完了 / 残課題 / 次回推奨）
3. ガントの `COMMENTS` に所見を追記（最新を上）
4. **push されているか確認**

> 「コミットして」「保存して」はセッション終了の合図ではない。
> 頼まれたファイルの更新とコミットだけを行い、締めの挨拶や完了宣言はしない。
