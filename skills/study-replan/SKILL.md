# study-replan — リプラン

## ★ 発火条件（User を待たない）

**Claude 側から必ず提案する**のは次のとき。User の申し出を待たない。

- 同一の軸・フェーズが **2週連続 🟡**
- **1回でも 🔴**
- 通し演習が合格ラインを **15pt 以上**下回った
- ある軸が **2週間、進捗ゼロ**

E資格では、信号（🟡🔴）は出していたが「**この軸を捨てる**」という構造提案には
至っていなかった。リプラン v2 も v3 も、発火したのは User 側だった。

> User の総括: 「v2 がちょっと遅かった。**私から提案したので、あなたから提案するべきでした**」
> 「軸B のスコープアウトも、**ちゃんと数字で詰められたら受け入れられたと思います**」
> 「長くやりすぎてる時は**早めにリプラン検討の連絡を入れて**ね」

## 提示の順序 — ★まず文章。ファイルは後

1. **文章で A / B / C 案を出す**（この時点でファイルは作らない）
2. User が選ぶ
3. **選ばれた案だけ**ガント新バージョンを作って提示

E資格では先にファイルを作ってしまい、作り直しの指示を出す手間が発生した。
User の指定: 「一気にファイル作ると長くなるので、**リプラン案はまず文章で。
そのあと作ってみて提示する**」。

## 3案の型（C案は必ず「捨てる案」にする）

| 案 | 性格 | 必ず添える数字 |
|---|---|---|
| **A案** | 総量を維持し、ペースを上げる | 必要ペース / 現在ペース / **その倍率** |
| **B案** | 総量を絞る（誤答限定・分野を絞る等） | 削減後の母数 / 必要ペース / **捨てる範囲のリスク** |
| **C案** | **軸を1本まるごと捨てる** | 捨てた分の時間 / それを何に回すか / **いつやるか（受験後 等）** |

**C案を必ず入れる。** 「頑張れば届く」案だけを並べると、破綻したときに退路がない。
E資格の v3（軸をまるごと捨てる案）は、実際にはこれが正解だった。

各案には必ず「**この案が破綻したと判定する条件と日付**」を書く（＝中間ゲート）。
判定は機械的に行う。「もう少し様子を見る」をしない。

## ★ 軸を捨てるときは、ゴールの記述まで書き換える

捨てた軸に紐づくゴールが `project-plan.md` に残っていたら、**同時に書き換える。**

- ✗ 「合格 + ◯◯ができるようになる」のまま軸を消す → 後で「未達」として残る
- ✓ ゴールを「合格」に絞り、「◯◯は本番後の Phase 2 で、△△から再開する」と明記する

E資格ではゴールが2つあり、片方をスコープアウトしたのにゴール記述を書き換えなかった。
振り返りで User は「3割くらい。写経止まり」と**未達として自己評価した**。
判断は正しかったのに、看板を下ろさなかったせいで失敗に見えてしまった。

## ガントのフォーク手順

1. `wbs-gantt_v<N>.html` を `wbs-gantt_v<N+1>.html` へ**コピー**する
2. 新しいほうだけ編集する。ベースライン `s`・`d` を新計画で引き直す
3. **旧版は編集しない。** 同じフォルダに凍結して残す
4. CONFIG の `VERSION` と `BASELINE` を書き換える
5. PNG を再生成して描画を目視確認する

> User の指定: 「バージョンは更新して、**旧バージョンは取っておいて**ほしい。
> 基本マスタプランはコロコロ変える想定ではないものなので」

**ベースラインを書き換えて遅れを消す**のが最悪の操作。遅れは「棒の後端 − 今日」で
自動表示されるので、棒を伸ばすと問題が見えなくなる。

## リプラン後にやること

- `project-plan.md` に**決定と根拠**を書く（何を捨て、なぜ、いつやるか）
- ガントの `COMMENTS` の先頭にリプラン発行のエントリを置く
- `STATUS.md` の信号と次ゲートを更新する
- **次のゲート日をカレンダー上の具体的な日付で言う**（「来週」ではなく「8/16(日)終了時」）
