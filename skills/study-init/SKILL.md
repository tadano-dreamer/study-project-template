# study-init — 立ち上げ（初日ゲートが本体）

テンプレート実体: `{{TEMPLATE_REPO}}/template/`

## ★ 最重要 — 初日ゲートを通すまで、教材を1文字も書かない

E資格プロジェクトで最大の反省がここ。**「地図」と「現在地」を両方とも最後に作った。**

| 本来やるべき時期 | 実際にやった時期 |
|---|---|
| 出題範囲（シラバス）との照合 | **受験前日** |
| 教材の目次を機械可読にする | **開始から2か月後** |
| 初見の実力測定 | **本番7日前** |

結果、本番で範囲改訂の新規項目が10問前後出て、対応できたのは1つだけだった。
**シラバス照合は30分で終わる作業**で、初日にやっていれば16週間の優先順位が全部変わっていた。

だから、この順序は動かさない。

### ゲート1: 出題範囲の一次資料を確保する

- 主催者の公式シラバス・出題範囲表・改訂履歴を**必ず一次情報で**取る（WebFetch/WebSearch を使う）
- **改訂の有無を確認する。** 「今年から追加された項目」「削除された項目」を明示的に列挙する
- 手に入らなければ、そのこと自体を `project-plan.md` にリスクとして書く

### ゲート2: 範囲と教材を機械可読な目次にする

- 出題範囲を**分野リスト**に落とす（後で台帳の「分野」列になる）
- 使う教材（問題集・講座・書籍）の**目次を全部取る**。
  動画講座なら講座番号まで。ここを作らないと、後で進捗を「何番まで見た」で受け取れない
- 出力先: `docs/範囲と教材.md`

### ゲート3: プレテストで現在地を測る

- **20〜30問**でよい。全範囲から薄く広く
- **確信度つき**で `ledger/` に記録する（→ `drill-ledger`）
- これが**全ての優先順位の根拠**になる。ここが無いまま計画を引くと、
  「どの分野が苦手か User 自身も分からない」状態のまま16週間走ることになる

### ゲート通過の判定

3つとも埋まったら、初めて WBS を引く。埋まらない項目があるなら、
**その項目を Phase 0 のタスクとしてガントの先頭に置き、期限を切る。**

## 生成するファイル

`{{TEMPLATE_REPO}}/template/` を新プロジェクトのフォルダへコピーし、以下を埋める。

| ファイル | 誰のためか | 中身 |
|---|---|---|
| `wbs-gantt/wbs-gantt_v1.html` | **人間（唯一の画面）** | CONFIG を埋める。Phase 0 に初日ゲートを置く |
| `project-plan.md` | AI | ゴール・KPI・軸の定義・週次計画・進捗ログ |
| `STATUS.md` | AI | 状態の圧縮スナップショット。毎セッション更新 |
| `THIS-WEEK.md` | 人間（軽く） | 今週やること。**日単位ではなく週単位** |
| `ledger/questions.tsv` | AI | 問題マスタ |
| `ledger/rounds/round1/` | **人間が触る唯一の記録先** | 解答ノート |
| `CLAUDE.md` | AI | プロジェクト固有のルール |
| `docs/範囲と教材.md` | AI | ゲート1・2の成果物 |

> `TODAY.md` は作らない。E資格では日単位で作ったが、User は初期しか見ず形骸化した。
> 実態は「土日にまとめて触る」なので、**週単位の `THIS-WEEK.md`** にする。

## ゴールの書き方（後で効く）

`project-plan.md` の冒頭に**ゴールを1つだけ**書く。複数あるなら優先順位を明記し、
**「捨てる順番」も先に決めておく**。

E資格ではゴールが「合格 + PyTorch で実装できるようになる」の2つあり、
途中で後者をスコープアウトしたのに**ゴールの記述を書き換えなかった**。
結果、後者は「未達」として残った。捨てるときは「いつやるか」まで書けば、
未達ではなく次フェーズへの送りになる。

## 立ち上げ時に User へ確認すること

決め打ちせず聞く。ただし**まとめて1回**で聞く（小出しにしない）。

1. **本番日（締切）と、逆算の起点にする日**
2. **可処分時間**の実態（平日/休日、どの端末で、どこで）
3. **教材**は何を使うか（既に持っているもの / これから買うもの）
4. **合格ライン**と、それを測る手段（過去問・模試の有無）
