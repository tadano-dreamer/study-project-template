# study-material — 教材生成

置き場所と役割: `materials/README.md` ／ **形（雛形・書き方の規則）の正本: `project-plan.md` §4**

## この仕事の位置づけ

E資格の振り返りで、学習者が「**これがなければ成立しなかった**」と挙げた唯一の項目が
**教材作成**だった。同時に、方針も評価されている:

> 「教材は解釈して翻訳する、原文写経はしない」→「**良かった。原文は読む分量じゃなかった。
>  あなたが理解しておいて、私の理解度に応じて適切な粒度のものを提供してくれるのが良い**」

だから **Claude が読んで噛み砕く。学習者に原文を読ませない。** これは崩さない。

統計検定2級（3週間・合格）では、教材の中心が「**書く → 読む → 返す**」の往復になった。
学習者が書いたもの（手書きの途中式・✍️ メモ）を Claude が全部読み、どこで取り違えたかを特定して、解説と図で返す。
学習者が次へ持ち出したいと挙げた上位3つ（過去問の解説・図解・一問一答の自動作成）は、どれもこの往復の部品だった。

---

## 作るもの。役割が違うので混ぜない

| 種類 | 役割 | いつ | 出力先 | 作る前に聞くか |
|---|---|---|---|---|
| ① **問題の解説** | 理解する（読み物の既定） | 演習を採点するたび・一問一答で落とすたび | `materials/問題の解説/` | 聞かない（中身） |
| ② **追加解説の図** | 形で見る | チャットで追加解説を頼まれたとき | `materials/図解/` | 聞かない |
| ③ **一問一答**（類題・暗記カード） | 想起する | 類題は誤答1つにつき1問 | `一問一答/` ＋ ★**`ledger/questions.tsv`** | 量と時刻は聞く（計画） |
| ④ **最終確認ノート** | 本番前に見る | 本番の約1週間前に Claude から提案 | `materials/最終確認ノート/` | 形と量の案を出して聞く |
| ⑤ 解釈ノート（分野ごと）・要点シート | 読んで理解する・通読する | 期間が長いとき | `materials/{分野名}/`・`materials/要点シート/` | **作る前に聞く** |

**作る教材の種類は「計画」なので、①②以外を増やすときは案を出して聞く。**
統計検定2級では解釈ノートを5本作ったが、読まれないまま過去問へ進み、読み物は問題の解説に一本化した。
解釈ノートについての学習者の答えは「作成前にユーザに聞くようにしましょう」。

---

## ★ 生成の順序は「弱い順」

```
python ledger/tally.py          # 分野別・4象限を見る
```

**正答率の低い分野から作る。進捗順・章立て順に作らない。**

E資格では最も苦手な分野が学習順序の最後に来た結果、
直前の圧縮フェーズで「時間が足りなくて相当駆け足」になり、
しかもその分野が**本番の冒頭7問**に出た。
**時間切れは必ず起きる前提で、切れたときに落ちるのが一番強い分野になるよう並べる。**

---

## ① 問題の解説 — チャットで聞き直さなくて済む深さで

雛形と規則は `project-plan.md` §4「問題の解説の形」。要点:

- **肢ごとの取り違えの表 → 根拠の1行 → 小さな数値例つきの仕組み → 例題3問**（答えはすぐ下。折りたたまない）
- 並びは ① 誤答・未回答 → ② 🤔つきの正解 → ③ 確信ありの正解（③ は表と根拠の1行だけ）
- 誤答の肢は**逆算して、どの計算・どの読み違いから出た数字かを書く**。
  `python ledger/tally.py` の混同パターン（**この学習者が実際に取り違えた肢のペア**）と、手書きページを見て書く。一般論の「よくある誤解」で埋めない
- **手書きページと ✍️ メモを全部読んでから書く。** 読んで分かった取り違えと、メモへの返事は、その問の解説の中に書く
  （ページ冒頭や管理ファイルに所見を書いても読まれない。同じ分析でも、解説の中に書いたものだけが届いた）
- 一問一答で落とした問いにも同じ形で書く（論点ごとに節。`python ledger/daily.py show <日付>` で見る）。
  統計検定2級では、解説を読んだ翌日の一問一答が 36% → 75% になった
- 教材の本文は転記しない。問題は教材と同じ呼び方で呼ぶ

> この形になった経緯: 短い要点シートを読んだ学習者が、25問のうち10問をチャットで聞き直した。
> 「今後の問題の解説も上記の構成でまとめるようにして欲しいです。
>  今回はobsidianに書いてあることをわざわざclaudeに追加解説聞く形で面倒でした」

## ② 追加解説の図

チャットで追加解説を頼まれたら、**図を SVG 1枚**で `materials/図解/` に描く
（計算の手順・面積・確率の分け方のように、形で見たほうが早い所）。

- 縦長・タブレットの幅で読める文字の大きさ。**描いたら画像にして自分の目で確かめてから渡す**
- Claude 用のメモは `materials/図解/追加解説メモ.md` の1枚に1節ずつ足す（形は `materials/README.md`）。図ごとに md を作らない（ファイルが倍に増える）
- **解説ファイルは書き換えない**（学習者「追加解説ごとに解説ファイルをアップデートしなくて良い」。チャットで説明した中身は、メモの「説明した要点」に残す）
- メモの「一問一答への反映」が **未** のものは、次に類題・暗記カードを足すときに拾う

## ③ 一問一答 — ★台帳から外さない

形は `project-plan.md` §4「一問一答の形」。**類題**（間違えた問題の確認）と**暗記カード**（即答すべき公式・定義）の2種類。

問いと答えの文面は `一問一答/類題/`・`一問一答/暗記カード/` の md に置き、**行を必ず `ledger/questions.tsv` に入れる**。

```
id	分野	型	正解	出典	メモ	元問題
類題-確率-01	A 確率と統計	選択	C	類題 1章	条件付き確率の向き	1-02-3
類題-確率-02	A 確率と統計	誤選択	B	類題 1章	最も不適切なものを選べ	1-02-3
暗記-確率-01	A 確率と統計	暗記	-	暗記カード 確率と統計	ベイズの定理の式	
```

**なぜ台帳に入れるか**: E資格ではフラッシュカードを495種の md にして外部ツールに投入した。
とてもよく効いたが、**正答率が一切残らなかった**。学習者はこれを唯一の明確な欠落として挙げている。
台帳に入っていれば、日替わりページ（`ledger/daily.py`）と `recall-drill` が **弱点順に出す・間隔反復で回す・正答率を記録する**。

- 類題は**誤答1つにつき1問**。`元問題` 列に元の問題 id を書く（元の象限を引き継いで出る）。解説の例題とは別の数値にする
- **`誤選択` 型を必ず何割か混ぜる**（「最も不適切なものを選べ」）。
  この型で落とす癖は、注意喚起では直らない。**出題に混ぜて数字にする**のが処方
- **手書きが要る計算は出さない**（暗算まで）。計算の取り違えは「どの式になるか」を選ぶ形にする
- **暗記カードの答えの頭に「⭕ の線」を1行書く**（どこまで言えたら⭕か）。
  線が無いと「迷ったら基本バツ」になり、本当に覚えていないカードと区別がつかない
- 素材を足したら `python ledger/daily.py check`
- 枚数をためらわない。学習者の評価は「**フラッシュカードは使い捨てのようなもので、苦手に応じてサクサク作り変えるもの**」。
  ただし**1日に出す量は別の話**で、立ち上げのときに User と決める（多すぎて、9日のうち7日は日付をまたいだ）

## ④ 最終確認ノート — ★本番の約1週間前に、Claude から提案する

2周目が終わったところで、Claude から形と量の案を出す。**前日に言い出されるのを待たない。**

> 統計検定2級では、本番の前日に学習者が言い出して作った。本番の朝に実際に見た教材はこれだった。
> 「2週目終わったくらいで提案するのが良いかもですね。前日よりは1週間前には一回区切ってほしいかも」

```
python ledger/tally.py --drill        # 全周回＋一問一答の記録から、まだ直っていないものだけ（弱い分野から）
```

の出力を材料にする。**記憶で作らない**（苦手の切り分けデータは台帳側にある）。

- **1ページ1トピック**。各ページは「ひとことで・中身・図・あなたの取り違え・こう出題される」
- 入れるのは「まだ直っていないもの」だけ。定着した項目を入れない
- 「あなたの取り違え」は、演習の誤答・手書き・✍️ メモから、実際の取り違えを書く
- 作り方は `materials/最終確認ノート/build.py`（`pages/*.html` を PDF にし、はみ出したページを報告する）
- 数式と数値は、書いたあとに検算する（できれば別のエージェントに）

## ⑤ 解釈ノート・要点シート（作ると決めたときだけ）

形は `materials/README.md`「解釈ノート」。論点ごとに区切り、さっと読める入口にする。
**「❌ 思い込み」は、実際に選んだ肢か、メモがあるときだけ書く。**

## 作る前にリサーチする

台帳に🔴が立っている項目は、**教材を書く前に公開情報を調べる**（WebSearch / WebFetch）。

> 「**あなたがネットからかき集めれば良かったのか。** 私のミスのキーワードから、
>  あなたが先に公開情報で予習しておくって感じ。
>  **あなたのリサーチ機能をうまく活用できてなかったですね**」

- 学習者に本から解説を貼り付けさせない（「本当は貼り付けは面倒ですよ」）
- **教材本文は転記しない**（著作権）。公開情報で概念を説明し直す
- シラバス改訂で追加された項目は特に、公開情報でしか埋まらないことが多い

---

## 大量生成のときは、着手前に分割単位を宣言する

> 「全◯分野を △分野ずつ、□回に分けます。各回の終わりでファイルを確定させるので、
>  途中で止まっても失われません。所要はおよそ ◯分です。」

E資格では問題集の一括読み込みでセッションの上限際どい状態が3日続いた。
**時間がかかるなら先に言う。**

---

## やらないこと

- **原文の写経**（解釈して翻訳する）
- **一問一答を台帳に入れずに md だけ置く**（正答率が残らなくなる）
- **略号のファイル名**（`FC03.md` `N3` `D5` のような。日本語の説明的な名前にする）
- **聞かずに教材の種類を増やす**（解釈ノート・要点シートは、作る前に聞く）
- **ページの冒頭や管理ファイルに所見を書く**（読まれない。解説の中に書く）
- **追加解説のたびに解説ファイルを書き換える**（図とメモを足す）
- **最終確認ノートを記憶で作る**（`tally.py --drill` から作る）
