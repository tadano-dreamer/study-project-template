# 設計思想 — なぜこの形なのか

このテンプレートの各設計判断が、**どの実測値・どの証言から来たか**を明記する。
納得できない判断は外して構わない。ただし**根拠を読んでから外してほしい**。

出典: E資格プロジェクト（2026-05-10 〜 2026-08-30 / 16週 / 遅れ0日で完走 / 結果は**合格**）の
振り返り一問一答100問。**合否発表前に**記録したものなので、
「合格したから全部正しかった」というバイアスがかかっていない。

## 判断1: 人間向けの画面はガント1枚に絞る

### 根拠

E資格では5階層のドキュメントを運用した。実際の利用状況はこうだった。

| ドキュメント | 学習者の実際の利用 |
|---|---|
| **ガント（HTML + PNG）** | **見た。行動を変えた** |
| 🟢🟡🔴 の3信号 | **意味のある区別だった。「赤から緑に変わった」と言われると嬉しい** |
| `TODAY.md`（当日タスク） | 初期のみ。中期の予定が明確で不要になった |
| `STATUS.md` | **「全然読んでいない。AI のためのファイル」** |
| 進捗管理セッションの分離 | **存在を知らなかった**（「そんなファイルあったんだ」） |
| `project-plan.md`（106KB） | 「私は読まないので、あなたが良い方法で」 |

### 導かれる設計

- ドキュメント階層は**冗長ではなかった**が、**人間向けは実質ゼロ**だった。
  「User に読ませる」設計目標を持たせたのが誤り
- → 数字・信号・遅延・コメントログを**全部ガントに載せる**
- → `STATUS.md` / `project-plan.md` / 進捗ログの構造は、**Claude の都合で最適化してよい**
  （明示的に委任されている）
- → `TODAY.md` は作らない。実態は「土日にまとめて触る」なので **`THIS-WEEK.md`**（週単位）

### やってはいけないこと

人間向けの新しいテキストファイルを増やす。読まれない。

## 判断2: 初日ゲート（地図と現在地）を最優先に置く

### 根拠

**同じ型の失敗が4件あった。** 「実力や範囲を測る行為」を全部後ろに置いていた。

| やるべき時期 | 実際にやった時期 | 遅れ |
|---|---|---|
| 出題範囲（シラバス2026）との照合 | **受験前日（8/29）** | 約16週 |
| 教材（全358講座）の目次を作る | **7/12**（開始から2か月） | 約9週 |
| 初見の実力測定（通し演習） | **8/23**（本番7日前） | — |
| 演習の本体に着手 | **7/4**（計画変更後） | 約8週 |

結果:
- 本番でシラバス新規項目が**10問前後**出題され、対応できたのは1大問だけ。残りは勘
- 学習者の総括: 「**これは大きなミス。初日にちゃんと詰めるべきでした、かなり後悔**」

シラバス照合は**30分で終わる作業**だった。やっていれば残り16週の優先順位が全部変わった。

### 導かれる設計

**ゲートが3つ埋まるまで、教材を1文字も書かない。**

1. 出題範囲の一次資料を確保（**改訂の有無を必ず確認**）
2. 範囲と教材を機械可読な目次にする
3. プレテスト 20〜30問で現在地を測る（確信度つき）

「初日に WBS を作れ」よりさらに手前。**WBS を引く材料がゲートの成果物**だから。

## 判断3: 正誤 × 確信の4象限で台帳を作る

### 根拠その1 — 逆行36%の正体

2周目で「1周目に正解した問題の 41/113 = 36%」を落とした。
Claude 側はこれを「忘却＝復習間隔の問題」と解釈していたが、学習者の実感は違った。

> 「**1周目がまぐれだと思う。自信のない回答を1周目でもっと拾うべきだった**（ほとんど勘）」

つまり**測定の問題**であって、定着の問題ではなかった。解き直しを増やしても直らない。

### 根拠その2 — 「たまたま正解」の導入が遅すぎた

確信度の自己申告は**本番7日前の通し演習から**始まった。そこで初めて
「正答率 67% のうち、確信ある正解は 53.6%」が見えた。13問が「たまたま正解」だった。

学習者は「**自己申告は正直でした。つけ漏れがない限り正確に反映されています**」と証言している。
つまり**仕組みさえあれば最初から正確に取れていた**。

### 根拠その3 — ❌ の付け忘れが27問

❌ を手でタップさせる運用にしたところ、付け忘れが27問発生し、演習の終盤に
判定の正本を「解説の貼付有無」へ切り替える是正が必要になった。

### 導かれる設計

- **正誤は自動判定**（問題マスタに正解を持たせ、選んだ肢から導く）。人のタップを減らす
- **確信度（🤔）だけは人がタップ**。これは人にしか付けられない。**1問目から**
- 4象限に分け、**🔴誤解 と ⚠️たまたま正解 で処方を変える**
  （前者は概念の再学習、後者は根拠の言語化。不正解だけを追うと後者が丸ごと見えない）
- **選んだ誤答肢を残す**（→ 判断5で使う）

## 判断4: 守らせたい作法は、全部「数字」に変換する

### 根拠

**効いたもの**（学習者の証言）:
- 「数字で詰めますって言われたのは**かなりやらなきゃなと思えました**」
- 遅延日数・必要ペース・逆行率・転換率 → 「**良かったです。行動を変えました**」
- 3信号 → 「**意味のある区別だった**」

**効かなかったもの**:
- 「最も不適切なものを選べ」型で落とす癖は、**対策を決めた後に同じ型でまた落ちた**
- 学習者の総括: 「スピードを出して解いてたから意識できなかった」
  「**声に出すとかそういうのは効果ない。ちゃんと仕組みで解決するようにしたい**」

### 導かれる設計

- 台帳に**設問タイプ列**（選択 / 誤選択 / 記述）を持たせ、
  **誤選択型だけの正答率**を別集計する → 差が10pt以上なら警告を出す
- 想起テストに**意図的にその型を混ぜる**
- 一般化: **注意喚起で直そうとしない。測って数字にして、出題に混ぜる**

### 「圧」の上限（学習者の指定）

1. 数字で突きつける（残日数・必要ペース・その差。感情を混ぜない）
2. **実行の宣言を求め、次のセッション冒頭で答え合わせをする**

ここまで。罰や機能停止のような演出はしない。**逃げ道は塞ぐが、学習は止めない。**

## 判断5: 想起テストは「教材」ではなく「台帳」から出す

### 根拠

E資格で学習効果の主エンジンだったのは Claude ではなく **NotebookLM** だった。
学習者が「効いた」と挙げた理由はほぼ全部そこに帰着する。

- 「知識として残った」理由 → *ノートブックLM に流して比較概念を表形式で見せてくれたので*
- 最大の伸び（ある分野が 28% → 69%）の理由 → *対比概念や「こんな誤解がある」を解説してくれたから*
- 一番効いた教材 → *フラッシュカード（NotebookLM の説明機能が大変役立った）*

Claude の貢献は「投入素材の生産」と「進捗の計器」に集約されていた。

一方で、明確な欠落が1つあった。

> 「**フラッシュカードの正答率とかは記録できなかった**ので、Claude Code でそれを
> 再現できるような良い土台があれば良いなと思いました」

### 導かれる設計

学習者の指定は「**依存は外す。ただし NotebookLM の機能を上回る価値を出すこと**」。
同じことをやるだけでは不足なので、**向こうに構造的に作れないもの**を出す。

| | 教材から作る道具 | このテンプレート |
|---|---|---|
| 出題順 | 教材の概念を等確率で | **4象限で優先度づけ**（🔴→⚠️→⬜→✅） |
| 対比表 | 教材にある一般的な対比 | ★**学習者が実際に取り違えた肢のペア**から作る |
| 誤解の指摘 | 「よくある誤解」 | ★**自信を持って間違えた記録**そのもの |
| 反復 | 毎回ゼロから | **間隔反復**（確信ある連続正解ごとに 1→2→4→8→16日） |
| 正答率 | 残らない | **`recall-log.tsv` に残り、次の出題順を変える** |

**個人化された混同カタログは、教材から一般論を作る道具には作れない。**
これが自作側の存在理由であり、これを作らないなら乗り換える意味がない。

## 判断6: リプランは Claude 側から発火する。C案は必ず「捨てる案」

### 根拠

信号（🟡🔴）は出していたが、「**この軸を捨てる**」という構造提案には至っていなかった。
計画変更が2回あったが、**どちらも発火したのは学習者側**だった。

> 「v2 がちょっと遅かった。**私から提案したので、あなたから提案するべきでした**」
> 「軸をまるごと捨てる案も、**ちゃんと数字で詰められたら受け入れられたと思います**」
> 「長くやりすぎてる時は**早めにリプラン検討の連絡を入れて**ね」

### 導かれる設計

- **発火条件を明文化**する: 2週連続🟡 / 1回でも🔴 / 通し演習が合格ライン -15pt / 2週間ゼロ進捗
- **C案（軸を1本捨てる案）を必ず入れる。** 「頑張れば届く案」だけ並べると退路がない
- **まず文章で提示し、選ばれた案だけファイルにする**
  （先にファイルを作って作り直しになった実例がある）
- **ベースラインは書き換えず、新バージョンへフォークして旧版を凍結**
  （棒を伸ばすと遅れが消えて見えなくなる。学習者も「旧バージョンは取っておいてほしい」と指定）

### 付随して必ずやること

**軸を捨てたら、ゴールの記述も書き換える。**

E資格ではゴールが2つあり、片方をスコープアウトしたのに記述を直さなかった。
振り返りで学習者はその部分を「3割くらい。写経止まり」と**未達として自己評価した**。
判断は正しかったのに、看板を下ろさなかったせいで失敗に見えた。

「捨てた」ではなく「**いつやるか**」を書けば、未達ではなく次フェーズへの送りになる。

## 判断7: 🟢 は「今は触らない」であって「もう安全」ではない

### 根拠

2周目で🟢判定を出して触らなかった3分野が、初見の通し演習で
**-18pt / -14pt / -9pt** と崩れた。逆に🔴を出して集中的に叩いた分野は
**+40pt / +35pt / +30pt / +25pt** と伸びた。

> 解釈: **やった分野は取れ、やらなかった分野は落ちた。それだけ。**

さらに構造的な問題があった。学習者は診断に参加していなかった。

> 「**どの分野が苦手、とかは自分では意識してなかった。**
> あなたの指示を信じて優先度高いものからやってたので」

全委任は学習者にとって成功だった（「任せる範囲はちょうど良い。狭めることはない」）。
問題は**冗長性がないこと** — Claude の診断が外れても、止める人がいない。

### 導かれる設計

- 🟢を出した分野には、**再測定の期限を `STATUS.md` に書く**
- 期限が来たら小テストで測り直す。**仕組みなので学習者の意識に依存しない**
- **既出問題の正答率は実力ではない。** 初見で測れる機会を本番の3週間前までに必ず1回置く

## 判断8: 弱い分野から処理する（特に直前期）

### 根拠

3つの不運が重なっていた。

1. 最後まで腹落ちしなかった分野が1つあった（16週間かけて唯一）
2. 直前1週間の圧縮フェーズで「**時間が足りなくて最後の2つは相当駆け足**」— その1つがこれ
3. 本番で「**初めの7問くらいがその分野**」で「全然分かりませんでした」

苦手分野を学習順序の**最後**に置いたため、**直前の時間切れリスクを一番弱い領域が丸ごと被った。**

### 導かれる設計

**直前圧縮フェーズの処理順は、進捗順ではなく「弱い順」にする。**

時間切れは必ず起きる前提で、切れたときに落ちるのが「一番強い分野」になるよう並べる。
分野別正答率は台帳にあるので、この並べ替えは自動化できる。

## 判断9: 内部語彙を会話に出さない

### 根拠

同じ症状が3件、独立に起きていた。

- 「**FC とか N とか D とか、ファイル名の由来よくわかんなかった**」
- 「`gen_2nd.py` / `tally_2nd.py` — **なんのファイルかわからないですが**、丸つけ用ですよね」
- 「『**安い絞り込み**』は何を指すかわからない」

3つ目は**振り返りの設問そのものが通じていなかった**。
16週間、Claude は自分の語彙で書き、学習者は推測で読んでいた。

### 導かれる設計

- **学習者が目にする名前・指標名は、すべて説明的な日本語**にする
- 略号は Claude 内部限定。会話に出さない
- **新しい指標の初出には、必ず1文の定義を添える**
- **1文で定義できない指標は導入しない**

（「逆行率」「転換率」「たまたま正解」は結果的に伝わった。
数字とセットで繰り返し出したからで、名前が良かったからではない。）

## 判断10: 処方には必ず「実行する器」を添える

### 根拠

「答えを見ずに手で書く」という処方は、**3回試して3回とも効いた**
（あるトピックで 30% → 95%、別のドリルで 5/14 → 14/14、ある大問で 0/4 → 4/4）。
効果はデータで確定していた。**それでも実行されなくなった。**

> 「手で書くって、デジタル勉強と相性が悪い。漢字ドリルみたいなしょっぱさがあった。
> **手書きする場所もなかったですし**」
> 「億劫だった。**書き込む内容もよくわからない**し効果もイマイチわからない」

失敗したのは説得ではなく**実行環境の未整備**だった。
iPad + Obsidian という環境は既にあったのに、**手書き用のテンプレートページを用意していなかった。**

対照的に、記録方式を手書きからチェックボックスへ移した瞬間に定着した
（「勉強はしやすくなりました」）。**摩擦を下げたら実行された。**

### 導かれる設計

**「やれ」だけの指示を出さない。** 処方を出すときは、
**成果物の置き場所と書式を同時に渡す。**

Claude 側のセルフチェック: 「この処方の**置き場所と書式を指定したか？**」

## 判断11: リサーチを学習ループの中に入れる

### 根拠

> 「**あなたがネットからかき集めれば良かったのか。** 私のミスのキーワードから、
> あなたが先に公開情報で予習しておくって感じ。
> **あなたのリサーチ機能をうまく活用できてなかったですね**」
> 「ネット情報にも良い教材はあるはずだが、**あなたに拾ってくることはできてなかった**」

Web 検索は使える状態にあったのに、学習ループに入っていなかった。
そのため間違えた問題の解説を**学習者が本から手で貼り付けていた**（「本当は面倒ですよ」）。

なお、1回だけ使った場面（本番前日のシラバス照合）では、**本番で実際に得点している。**

### 導かれる設計

- 台帳に🔴が立った時点で、**そのキーワードの公開情報を Claude が先に調べる**
- 学習者の作業は「間違えた」を記録するところで完結させる
- 教材本文は転記させない（著作権）。**公開情報で概念を説明し直す**

## 判断12: モバイル同期の構成は、そのまま持っていく

### 根拠

```
Claude Code (PC) → GitHub → Working Copy (iPhone) → iCloud → Obsidian (iPad)
                       └→ ガント PNG を GitHub 上で閲覧
```

- 「**このアーキテクチャはとても満足していました**」
- 「Claude がコードを実行できない制約は**ほとんど足を引っ張らなかった**」
- 「ガント PNG は使いました。**GitHub からパッと見ることができました**」
- 「これは良かった。**ぜひ今後もやる**」

**唯一の不具合**: Jupyter ノートブック（`.ipynb`）がスマホの Git クライアントで壊れ、
削除済みファイルがステージングに残り続けた。

### 導かれる設計

- この構成を `docs/03_環境.md` にそのまま同梱する
- **`.ipynb` は既定で `.gitignore`**。追跡が必要なときだけ明示的に外す
- ガントは**必ず PNG も生成する**（スマホの GitHub は JavaScript を実行しないため）

## 最後に — この振り返りをどう読むべきか

学習者の総括はこうだった。

> 「AI 使ってよくできたと思う。でも **AI 進捗管理の整備に結構時間を割いた**ところもあるので、
> 次回はこのテンプレをもとに**素早く構築**していきましょう」

**このテンプレートの目的は、その「整備の時間」をゼロにすること。**
仕組みを作ることが目的化したら、それは失敗している。
