# 設計思想 — なぜこの形なのか

このテンプレートの各設計判断が、**どの実測値・どの証言から来たか**を明記する。
納得できない判断は外して構わない。ただし**根拠を読んでから外してほしい**。

出典は2つのプロジェクトの振り返り。

- **判断1〜12**: E資格プロジェクト（2026-05-10 〜 2026-08-30 / 16週 / 遅れ0日で完走 / 結果は**合格**）の
  振り返り一問一答100問。**合否発表前に**記録したものなので、
  「合格したから全部正しかった」というバイアスがかかっていない。
- **判断13〜18 と、判断1 の追記**: このテンプレートを使った統計検定2級プロジェクト（2026-09-23 〜 2026-10-11 / 3週 /
  遅れは最大1日 / 結果は**合格**）の振り返り41問。こちらは CBT で当日に結果が出たので、結果を知ったあとの記録になる。
  そのため、効いたかどうかは合否ではなく、回答に出た摩擦（読んだか・時間・迷い）で判定した。
  学習者は準1級の受験経験があり、期間中は1日4時間ほど取れた。条件が恵まれていた点は割り引いて読んでほしい。

## 判断1: 人間向けの画面を絞る（進み具合はガント1枚。追記で、学習ページと今週やることを足した）

### 根拠

E資格では5階層のドキュメントを運用した。実際の利用状況はこうだった。

| ドキュメント | 学習者の実際の利用 |
|---|---|
| **ガント（HTML + PNG）** | **見た。行動を変えた** |
| 🟢🟡🔴 の3信号 | **意味のある区別だった。「赤から緑に変わった」と言われると嬉しい** |
| `TODAY.md`（当日タスク） | 初期のみ。中期の予定が明確で不要になった |
| `STATUS.md` | **「全然読んでいない。AI のためのファイル」** |
| 進捗管理セッションの分離 | **存在を知らなかった**（「そんなファイルあったんだ」） |
| `project-plan.md`（106KB） | 「私は読まないので、あなたが良い方法で」 |

### 導かれる設計

- ドキュメント階層は**冗長ではなかった**が、**人間向けは実質ゼロ**だった。
  「User に読ませる」設計目標を持たせたのが誤り
- → 数字・信号・遅延・コメントログを**全部ガントに載せる**
- → `STATUS.md` / `project-plan.md` / 進捗ログの構造は、**Claude の都合で最適化してよい**
  （明示的に委任されている）
- → `TODAY.md` は作らない。実態は「土日にまとめて触る」なので **`THIS-WEEK.md`**（週単位）

### やってはいけないこと

人間向けの新しいテキストファイルを増やす。読まれない。

### 追記（統計検定2級）: 読まれるかどうかは、中身ではなく置き場所で決まる

2回目のプロジェクトでも、同じことが起きた。

| Claude が書いたもの | 学習者の実際の利用 |
|---|---|
| ガント（スマホで PNG） | 見た。イナズマ線とバーの色を見ていた |
| 解答ノート・問題の解説・図・一問一答のページ | 毎日開いた |
| `THIS-WEEK.md`（週単位に変えたもの） | 「**結局thisweekは見なかったな**」「ガントチャートで教えてくれるから見なくて良かった」 |
| `STATUS.md`・`project-plan.md` | 「**全部自分では全くみてない**」 |
| 一問一答ページの冒頭に、毎晩書いた所見 | 「**冒頭の長いコメントは読んでなかった**」「一問一答の解説があれば十分だった」 |
| 分野ごとの解釈ノート5本 | 読まないまま過去問へ進んだ |

手書きの分析は「助かりました」と言われたが、それは**解説の中に書いたから**届いた。
同じ分析でも、ページ冒頭の所見に書いたものは届いていない。

- → 人が見る画面は「ガント・学習ページ（解答ノート・解説・図・一問一答）・`THIS-WEEK.md`」の3つと決める
- → 所見は解説の中に書く。ページの冒頭や管理ファイルに書かない
- → `THIS-WEEK.md` は、E資格の `TODAY.md` と合わせて2回続けて開かれなかった。学習者の見立ては
  「**常にやってないものがパッと上に出れば良かったのだと思います。できたものは下の方にトグルで隠しつつ書いておくとか**」。
  済んだ行が上に積もり、まだやっていない行が埋もれていたので、並び方を直して残した。
  **次の振り返りで、開いたかを必ず聞く**（開かれなければ、やめてガントに寄せる）

## 判断2: 初日ゲート（地図と現在地）を最優先に置く

### 根拠

**同じ型の失敗が4件あった。** 「実力や範囲を測る行為」を全部後ろに置いていた。

| やるべき時期 | 実際にやった時期 | 遅れ |
|---|---|---|
| 出題範囲（シラバス2026）との照合 | **受験前日（8/29）** | 約16週 |
| 教材（全358講座）の目次を作る | **7/12**（開始から2か月） | 約9週 |
| 初見の実力測定（通し演習） | **8/23**（本番7日前） | — |
| 演習の本体に着手 | **7/4**（計画変更後） | 約8週 |

結果:
- 本番でシラバス新規項目が**10問前後**出題され、対応できたのは1大問だけ。残りは勘
- 学習者の総括: 「**これは大きなミス。初日にちゃんと詰めるべきでした、かなり後悔**」

シラバス照合は**30分で終わる作業**だった。やっていれば残り16週の優先順位が全部変わった。

### 導かれる設計

**ゲートが3つ埋まるまで、教材を1文字も書かない。**

1. 出題範囲の一次資料を確保（**改訂の有無を必ず確認**）
2. 範囲と教材を機械可読な目次にする
3. プレテスト 20〜30問で現在地を測る（確信度つき）

「初日に WBS を作れ」よりさらに手前。**WBS を引く材料がゲートの成果物**だから。

## 判断3: 正誤 × 確信の4象限で台帳を作る

### 根拠その1 — 逆行36%の正体

2周目で「1周目に正解した問題の 41/113 = 36%」を落とした。
Claude 側はこれを「忘却＝復習間隔の問題」と解釈していたが、学習者の実感は違った。

> 「**1周目がまぐれだと思う。自信のない回答を1周目でもっと拾うべきだった**（ほとんど勘）」

つまり**測定の問題**であって、定着の問題ではなかった。解き直しを増やしても直らない。

### 根拠その2 — 「たまたま正解」の導入が遅すぎた

確信度の自己申告は**本番7日前の通し演習から**始まった。そこで初めて
「正答率 67% のうち、確信ある正解は 53.6%」が見えた。13問が「たまたま正解」だった。

学習者は「**自己申告は正直でした。つけ漏れがない限り正確に反映されています**」と証言している。
つまり**仕組みさえあれば最初から正確に取れていた**。

### 根拠その3 — ❌ の付け忘れが27問

❌ を手でタップさせる運用にしたところ、付け忘れが27問発生し、演習の終盤に
判定の正本を「解説の貼付有無」へ切り替える是正が必要になった。

### 導かれる設計

- **正誤は自動判定**（問題マスタに正解を持たせ、選んだ肢から導く）。人のタップを減らす
- **確信度（🤔）だけは人がタップ**。これは人にしか付けられない。**1問目から**
- 4象限に分け、**🔴誤解 と ⚠️たまたま正解 で処方を変える**
  （前者は概念の再学習、後者は根拠の言語化。不正解だけを追うと後者が丸ごと見えない）
- **選んだ誤答肢を残す**（→ 判断5で使う）

## 判断4: 守らせたい作法は、全部「数字」に変換する

### 根拠

**効いたもの**（学習者の証言）:
- 「数字で詰めますって言われたのは**かなりやらなきゃなと思えました**」
- 遅延日数・必要ペース・逆行率・転換率 → 「**良かったです。行動を変えました**」
- 3信号 → 「**意味のある区別だった**」

**効かなかったもの**:
- 「最も不適切なものを選べ」型で落とす癖は、**対策を決めた後に同じ型でまた落ちた**
- 学習者の総括: 「スピードを出して解いてたから意識できなかった」
  「**声に出すとかそういうのは効果ない。ちゃんと仕組みで解決するようにしたい**」

### 導かれる設計

- 台帳に**設問タイプ列**（選択 / 誤選択 / 記述）を持たせ、
  **誤選択型だけの正答率**を別集計する → 差が10pt以上なら警告を出す
- 想起テストに**意図的にその型を混ぜる**
- 一般化: **注意喚起で直そうとしない。測って数字にして、出題に混ぜる**

### 「圧」の上限（学習者の指定）

1. 数字で突きつける（残日数・必要ペース・その差。感情を混ぜない）
2. **実行の宣言を求め、次のセッション冒頭で答え合わせをする**

ここまで。罰や機能停止のような演出はしない。**逃げ道は塞ぐが、学習は止めない。**

## 判断5: 想起テストは「教材」ではなく「台帳」から出す

### 根拠

E資格で学習効果の主エンジンだったのは Claude ではなく **NotebookLM** だった。
学習者が「効いた」と挙げた理由はほぼ全部そこに帰着する。

- 「知識として残った」理由 → *ノートブックLM に流して比較概念を表形式で見せてくれたので*
- 最大の伸び（ある分野が 28% → 69%）の理由 → *対比概念や「こんな誤解がある」を解説してくれたから*
- 一番効いた教材 → *フラッシュカード（NotebookLM の説明機能が大変役立った）*

Claude の貢献は「投入素材の生産」と「進捗の計器」に集約されていた。

一方で、明確な欠落が1つあった。

> 「**フラッシュカードの正答率とかは記録できなかった**ので、Claude Code でそれを
> 再現できるような良い土台があれば良いなと思いました」

### 導かれる設計

学習者の指定は「**依存は外す。ただし NotebookLM の機能を上回る価値を出すこと**」。
同じことをやるだけでは不足なので、**向こうに構造的に作れないもの**を出す。

| | 教材から作る道具 | このテンプレート |
|---|---|---|
| 出題順 | 教材の概念を等確率で | **4象限で優先度づけ**（🔴→⚠️→⬜→✅） |
| 対比表 | 教材にある一般的な対比 | ★**学習者が実際に取り違えた肢のペア**から作る |
| 誤解の指摘 | 「よくある誤解」 | ★**自信を持って間違えた記録**そのもの |
| 反復 | 毎回ゼロから | **間隔反復**（確信ある連続正解ごとに 1→2→4→8→16日） |
| 正答率 | 残らない | **`recall-log.tsv` に残り、次の出題順を変える** |

**個人化された混同カタログは、教材から一般論を作る道具には作れない。**
これが自作側の存在理由であり、これを作らないなら乗り換える意味がない。

## 判断6: リプランは Claude 側から発火する。C案は必ず「捨てる案」

### 根拠

信号（🟡🔴）は出していたが、「**この軸を捨てる**」という構造提案には至っていなかった。
計画変更が2回あったが、**どちらも発火したのは学習者側**だった。

> 「v2 がちょっと遅かった。**私から提案したので、あなたから提案するべきでした**」
> 「軸をまるごと捨てる案も、**ちゃんと数字で詰められたら受け入れられたと思います**」
> 「長くやりすぎてる時は**早めにリプラン検討の連絡を入れて**ね」

### 導かれる設計

- **発火条件を明文化**する: 2週連続🟡 / 1回でも🔴 / 通し演習が合格ライン -15pt / 2週間ゼロ進捗
- **C案（軸を1本捨てる案）を必ず入れる。** 「頑張れば届く案」だけ並べると退路がない
- **まず文章で提示し、選ばれた案だけファイルにする**
  （先にファイルを作って作り直しになった実例がある）
- **ベースラインは書き換えず、新バージョンへフォークして旧版を凍結**
  （棒を伸ばすと遅れが消えて見えなくなる。学習者も「旧バージョンは取っておいてほしい」と指定）

### 付随して必ずやること

**軸を捨てたら、ゴールの記述も書き換える。**

E資格ではゴールが2つあり、片方をスコープアウトしたのに記述を直さなかった。
振り返りで学習者はその部分を「3割くらい。写経止まり」と**未達として自己評価した**。
判断は正しかったのに、看板を下ろさなかったせいで失敗に見えた。

「捨てた」ではなく「**いつやるか**」を書けば、未達ではなく次フェーズへの送りになる。

## 判断7: 🟢 は「今は触らない」であって「もう安全」ではない

### 根拠

2周目で🟢判定を出して触らなかった3分野が、初見の通し演習で
**-18pt / -14pt / -9pt** と崩れた。逆に🔴を出して集中的に叩いた分野は
**+40pt / +35pt / +30pt / +25pt** と伸びた。

> 解釈: **やった分野は取れ、やらなかった分野は落ちた。それだけ。**

さらに構造的な問題があった。学習者は診断に参加していなかった。

> 「**どの分野が苦手、とかは自分では意識してなかった。**
> あなたの指示を信じて優先度高いものからやってたので」

全委任は学習者にとって成功だった（「任せる範囲はちょうど良い。狭めることはない」）。
問題は**冗長性がないこと** — Claude の診断が外れても、止める人がいない。

### 導かれる設計

- 🟢を出した分野には、**再測定の期限を `STATUS.md` に書く**
- 期限が来たら小テストで測り直す。**仕組みなので学習者の意識に依存しない**
- **既出問題の正答率は実力ではない。** 初見で測れる機会を本番の3週間前までに必ず1回置く

## 判断8: 弱い分野から処理する（特に直前期）

### 根拠

3つの不運が重なっていた。

1. 最後まで腹落ちしなかった分野が1つあった（16週間かけて唯一）
2. 直前1週間の圧縮フェーズで「**時間が足りなくて最後の2つは相当駆け足**」— その1つがこれ
3. 本番で「**初めの7問くらいがその分野**」で「全然分かりませんでした」

苦手分野を学習順序の**最後**に置いたため、**直前の時間切れリスクを一番弱い領域が丸ごと被った。**

### 導かれる設計

**直前圧縮フェーズの処理順は、進捗順ではなく「弱い順」にする。**

時間切れは必ず起きる前提で、切れたときに落ちるのが「一番強い分野」になるよう並べる。
分野別正答率は台帳にあるので、この並べ替えは自動化できる。

同じ症状が3件、独立に起きていた。

- 「**FC とか N とか D とか、ファイル名の由来よくわかんなかった**」

（「逆行率」「転換率」「たまたま正解」は結果的に伝わった。
数字とセットで繰り返し出したからで、名前が良かったからではない。）

## 判断10: 処方には必ず「実行する器」を添える

### 根拠

「答えを見ずに手で書く」という処方は、**3回試して3回とも効いた**
（あるトピックで 30% → 95%、別のドリルで 5/14 → 14/14、ある大問で 0/4 → 4/4）。
効果はデータで確定していた。**それでも実行されなくなった。**

> 「手で書くって、デジタル勉強と相性が悪い。漢字ドリルみたいなしょっぱさがあった。
> **手書きする場所もなかったですし**」
> 「億劫だった。**書き込む内容もよくわからない**し効果もイマイチわからない」

失敗したのは説得ではなく**実行環境の未整備**だった。
iPad + Obsidian という環境は既にあったのに、**手書き用のテンプレートページを用意していなかった。**

対照的に、記録方式を手書きからチェックボックスへ移した瞬間に定着した
（「勉強はしやすくなりました」）。**摩擦を下げたら実行された。**

### 導かれる設計

**「やれ」だけの指示を出さない。** 処方を出すときは、
**成果物の置き場所と書式を同時に渡す。**

Claude 側のセルフチェック: 「この処方の**置き場所と書式を指定したか？**」

## 判断11: リサーチを学習ループの中に入れる

### 根拠

> 「**あなたがネットからかき集めれば良かったのか。** 私のミスのキーワードから、
> あなたが先に公開情報で予習しておくって感じ。
> **あなたのリサーチ機能をうまく活用できてなかったですね**」
> 「ネット情報にも良い教材はあるはずだが、**あなたに拾ってくることはできてなかった**」

Web 検索は使える状態にあったのに、学習ループに入っていなかった。
そのため間違えた問題の解説を**学習者が本から手で貼り付けていた**（「本当は面倒ですよ」）。

なお、1回だけ使った場面（本番前日のシラバス照合）では、**本番で実際に得点している。**

### 導かれる設計

- 台帳に🔴が立った時点で、**そのキーワードの公開情報を Claude が先に調べる**
- 学習者の作業は「間違えた」を記録するところで完結させる
- 教材本文は転記させない（著作権）。**公開情報で概念を説明し直す**

## 判断12: モバイル同期の構成は、そのまま持っていく

### 根拠

```
Claude Code (PC) → GitHub → Working Copy (iPhone) → iCloud → Obsidian (iPad)
                       └→ ガント PNG を GitHub 上で閲覧
```

- 「**このアーキテクチャはとても満足していました**」
- 「Claude がコードを実行できない制約は**ほとんど足を引っ張らなかった**」
- 「ガント PNG は使いました。**GitHub からパッと見ることができました**」
- 「これは良かった。**ぜひ今後もやる**」

**唯一の不具合**: Jupyter ノートブック（`.ipynb`）がスマホの Git クライアントで壊れ、
削除済みファイルがステージングに残り続けた。

### 導かれる設計

## 判断13: 学習の中心は「書く → 読む → 返す」の往復に置く

### 根拠

統計検定2級で、学習者が「次の学習へ持ち出したい仕組み」の上位3つに挙げたのは、
過去問の解説・図解・一問一答の自動作成だった。満足の理由として挙がったのも「**特に手書き周りの分析**」。

| 部品 | 学習者の評価 |
|---|---|
| 問題の解説（肢ごとの取り違えの表 → 根拠の1行 → 数値例つきの仕組み → 例題3問） | 「解説ファイルと追加解説の図式の運用は**かなりよかった**」 |
| 追加解説の図（SVG 1枚） | 「**svgかなり見やすかったです**」「グラフを用いた説明があるのが良かった」 |
| 手書きページを Claude が全部読む | 「**これ1番重要ですね**」「ミスポイント見つけてくれて助かりました」 |
| 一問一答で落とした問いの解説（学習者の提案で追加） | 解説を読んだ翌日のページは、正答率が 36% → 75% |
| ✍️ メモ欄 | 「私の書き込み場所として**かなり役立ちました**」 |

学習者が書いたもの（手書きの途中式・✍️ メモ）を Claude が全部読み、どこで取り違えたかを特定して、解説と図で返していた。
学習者は「原因究明や解説をclaudeに託していた」ので、採点のあとの赤ペンの直しは書かなかった（275枚中1枚）。
直す役が、学習者の赤ペンから Claude の解説へ移っていた。

判断5 の宿題（「NotebookLM への依存を外す。ただし上回る価値を出す」）は、これで片づいた。
今回は NotebookLM を使わず、同じ役目を Claude が果たしている。

この形になったきっかけは、短い要点シートだった。25問ぶんを読んだ学習者が、10問をチャットで聞き直した。

> 「今後の問題の解説も上記の構成でまとめるようにして欲しいです。
> 今回はobsidianに書いてあることを**わざわざclaudeに追加解説聞く形で面倒でした**」

### 導かれる設計

- 採点のあとの解説は、**チャットで聞き直さなくて済む深さで、最初からファイルに書く**（形は `template/project-plan.md` §4）
- **読み物はこの1種類を既定にする。** 分野ごとのノートと2本立てにすると、同じ説明が2か所に出て、片方は読まれない
- **小問ごとに手書きページを用意し、Claude が全部読む。** 既定は「あり」
- 追加解説は**図1枚**。解説ファイルは書き換えず、Claude 用のメモを1ファイルに積む
- 一問一答のページは定期実行で毎日作る。学習者は pull → 解く → push だけ

### この相性が成り立つ条件

学習者はこの相性の良さを「**解答もあったので**」「資格の性質かな」と見ている。
正解が手元にある選択式の試験だったから、Claude が取り違えを特定できた。記述式や、正解の無い学習では、同じようには働かない。

## 判断14: 計画は聞く。中身は聞かずに進める

### 根拠

別々の設問への回答7件が、同じ1本の線の上にあった。

| 学習者の回答 | 属するもの |
|---|---|
| 「**学習内容など事実は進めて良かった。計画周りは聞いて欲しい**」 | 線そのもの |
| 計画は、Claude が決めた部分を全部見せて、聞いてから発行する →「続ける」 | 日程 |
| 分野ごとのノートを作るか →「作成前にユーザに聞くようにしましょう」 | 作る教材の種類 |
| 定期実行の時刻 →「その時々で変わるかと思うので聞いてあげてください」 | 時刻 |
| 一問一答の量 →「ここはタイプによって都度確認ですね」 | 量 |
| 追加の教材を買うか →「こっちに聞かないで進めようとしたので、気になった」 | 買う物 |
| Claude が聞いてくる量とタイミング →「ちょうど良かった」 | — |

Claude の失敗は、この線の両側で起きていた。

- **聞かずに進めかけた**: 追加の教材を買うか買わないか
- **聞きに行かなかった**: 一問一答の量（→ 判断15）と、直前の教材（→ 判断16）

一方で、「判断を委ねられたら、選択肢を並べず決めて実行する」という決まりも生きている。確かめると、こうだった。

> 「任されたら決めて実行する、が既定で良いです。必要なら私が『**まず計画だけ**』みたいに言うので」

外れていたのは決まりではなく、切り替えの合図を決めていなかったことだった。

### 導かれる設計

| 学習者の言い方 | 計画（日程・量・時刻・作る教材の種類・買う物） | 中身（解説・図・採点・分析） |
|---|---|---|
| 何も言われていない | 案を出して聞く | 聞かずに進める |
| 「任せる」 | 決めて実行する | 聞かずに進める |
| 「まず計画だけ」 | 案を1つ出して止まる | 聞かずに進める |

判定の線を先に決めておくやり方（中間ゲート）は、この線に沿ってうまく動いた
（「**事実の判定と意思決定はかなり役だった**」）。線は一緒に決め、判定は Claude が数字で機械的に行い、最後に決めるのは学習者。

## 判断15: 器を置いたら、それを見て動く決まりも置く

### 根拠

一問一答は「毎日30分・過去問とは別」で始めた。実際は違った。

- 「30分以上かかって、長期的に毎日、だと少ししんどかったかも」
- 9日のうち7日は、日付が変わってから解いていた（深夜2日・翌朝5日）
- 量を調整するための「かかった時間」の欄は、**9日のうち1日しか書かれなかった**
- 途中で類題を1日6問から12問に増やした（総数は同じ。類題は選択式で、考える時間が要る）

量の上限を決めたのは最初の1回だけで、そのあとの調整は「欄に書いてもらえれば直す」という、学習者が書くのを待つ仕組みだった。
学習者は「解いた後の連絡はしない」と決めていたので、欄は空のままだった。
push の時刻は git に残っていて、日付をまたいだことは記録から分かったのに、学習中に Claude から量を減らす案は出ていない。

判断10（処方には器を添える）と同じ型だが、今回は器が無かったのではない。**記録を見て動く決まりが無かった。**

### 導かれる設計

- 1日の量は、**解説を読む時間まで含めて**、始めに学習者と決める（量は計画 → 判断14）
- 量が多すぎないかは、学習者の申告ではなく **push の時刻**で見る（`python ledger/daily.py pace`）
- **日付をまたいで解いた日が2日続いたら、Claude から減らす案を出す。** セッションの始めに毎回見る
- 一般化: 記録の欄を作るときは、「誰が・いつ・それを見て何をするか」まで決める。人が書くのを待つ欄にしない

## 判断16: 直前の教材は、本番の約1週間前に Claude から提案する

### 根拠

本番の朝に学習者が実際に見た教材は、**前日に学習者自身が言い出して作ったもの**だった
（くり返し落とした論点を1ページ1トピックにまとめた「最終確認ノート」）。

> 「2週目までで間違えたもの一問一答でずっと間違えてるものを一気にまとめたかったのです」
> 「2週目終わったくらいで提案するのが良いかもですね。**前日よりは1週間前には一回区切ってほしいかも**」

計画に行が無く、Claude からも提案していなかった。
E資格の反省で「直前の圧縮は台帳から自動で作る」と決めていたが、道具（`tally.py --drill`）が1周回しか見なかったので、
2周目で解き直さなかった誤答も、一問一答で落とし続けている問いも出ず、使い捨てのスクリプトで材料を作ることになった。

### 導かれる設計

- ガントの最初の版に「**直前の教材を提案**」の行を置く（本番の約1週間前・2周目が終わるところ）
- 形は1ページ1トピック: ひとことで・中身・図・**あなたの取り違え**・こう出題される
- `tally.py --drill` は、全周回と一問一答の記録をまとめ、**まだ直っていないものだけ**を弱い分野から出す

## 判断17: 期間の短さで決まった運用を、次の既定にしない

### 根拠

学習者は5つの運用について、「今回は3週間だったから」と断っている。

| 運用 | 学習者の回答 |
|---|---|
| 分野ごとのノートを作らない | 「今回は時間がなかった故の対応」「長く資格勉強するならいるかな」 |
| 周回数（2周＋任意の3周目） | 「これも期間による。長ければ4,5週目までやるかと」 |
| 予備の過去問を使わない | 「どっかでチェックポイント設けて追加で買うか検討すると良いかもね」 |
| 一問一答の量 | 「今回は期日の短さもあったかと思う」 |
| 採点のあとの直しを書かない | 「今回はスピード感も必要だった」 |

### 導かれる設計

立ち上げのときに、**期間から決めること**の表を埋める（`template/project-plan.md` §3）。
どれも計画なので、Claude が案を出して学習者に聞く（判断14）。前のプロジェクトの値を既定にしない。

## 判断18: 振り返りは、学習中の発言の記録を軸にする

### 根拠

統計検定2級では、学習中の指摘・要望・決定を、その場で計画書の末尾に1行ずつ書き写していた（77行）。
きっかけは学習者の一言だった。

> 「あなたが指摘ごとに覚えておいて、それベースで最後振り返るほうが**圧倒的に早いですよね？**」

その結果、振り返りの設問は E資格の100問に対して41問（必須は19問）で足りた。

- 「**設問少ないからそんな苦労しなかった**」「1問ずつデフォルトはこのチャット上でできるとよい」
- 一方で「何回か何の質問？ってのありましたね」。止まった4問は、どれも Claude の側にしか見えない仕組みの名前や、
  過去のやり取りの細かい段階を聞いていた（判断9 と同じ型）
- 本番の中身は記録に残らなかった。CBT は当日に結果が出るうえ、振り返りを始めたのが4日後だったので、
  5日後の回答は「全くわからなかったのが6問くらいありました。**どの単元かは忘れた**」

### 導かれる設計

- 学習中の発言は、**言われた言葉のまま、その場で** `project-plan.md` §6 に足す。Claude の道具で、学習者は意識しなくてよい
- 振り返りは40問前後（必須は半分）・チャットで1問ずつ、を既定にする
- Claude 側の仕組みを聞くときは、**学習者から見えていた形**で書く
- **本番の報告を受けた同じ返事で、3つ聞く**（分からなかった問題の分野と中身・時間配分・手応え）
- 直した形が効いたかは、次の学習で確かめる。`study-init` の表が次のプロジェクトの `project-plan.md` §7 に写され、
  次の振り返りで結果が書かれる

## 最後に — この振り返りをどう読むべきか

学習者の総括はこうだった。

> 「AI 使ってよくできたと思う。でも **AI 進捗管理の整備に結構時間を割いた**ところもあるので、
> 次回はこのテンプレをもとに**素早く構築**していきましょう」

**このテンプレートの目的は、その「整備の時間」をゼロにすること。**
仕組みを作ることが目的化したら、それは失敗している。

2回目（統計検定2級）の総括はこうだった。

> 「**最低限の勉強量で確実に合格できました。負荷も高くなかったので良い管理でした**」

ただし、合格に仕組みがどれだけ寄与したかは切り分けられない（学習者は「もともと落ちる気はしなかった」と答えている）。
仕組みは、合否ではなく負荷で評価する。
